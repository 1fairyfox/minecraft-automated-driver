# 2026-07-25 — Multi-target scenarios (0.15.0) + security hardening for inbound content (0.16.0)

## Done (0.16.0 — security: inbound / untrusted content)

- Owner flagged (mid-session) a second trust boundary the posture hadn't addressed: not the listener/
  enablement surface (already covered — stdio-only, loopback+token, agents off by default) but **what
  the tool processes from a server/client/download it connects to**. On a code system like Minecraft,
  one wrong plugin/server/download can feed crafted input to code we run.
- **Threat model** `notes/security/threat-model.md` — surface-by-surface with blast radius + stance +
  residual + guidance: (1) untrusted server → the in-process Mineflayer packet parser (the sharpest —
  blast radius is the driver process); (2) hostile server → agent-enabled client + control-plane
  amplification; (3) co-resident malicious plugin/mod reading the loopback token; (4) supply chain of
  downloaded Paper / deployed plugin jars; (5) `build_gradle` = arbitrary exec by design; (6) console
  authority; (7) DoS buffering (already handled by bounded ring buffers). Plus an operator "brace list".
- **Two guardrails** (the places the tool could *silently* process untrusted input):
  - `bot_join`/scenario `bot` **refuse a non-loopback host unless `allowRemote:true`** — a bot parses
    the server's packets in the driver process, so the in-process parser is never aimed at an untrusted
    remote by accident. `isLoopbackHost` exported + wired through.
  - **Paper jar SHA-256 verification** — hash the download as it streams (single-pass tee), verify vs
    PaperMC's published `checksums.sha256`, **fail closed** (delete + throw) on mismatch. Confirmed the
    fill v3 API exposes `checksums.sha256` before coding.
- `SECURITY.md` gains an "Inbound / untrusted content" section; `CLAUDE.md` security model +
  `decisions/architecture.md` record it as a standing boundary.
- **Tests:** 177 driver tests (bot loopback guard: refuse remote / `allowRemote` opt-in / `isLoopbackHost`
  forms; Paper integrity: match keeps / mismatch rejects + deletes / checksum carried). c8 99.10% lines /
  91.95% branches — gate held. `check-links`, `npm audit` (0), `build-docs` green. Default local workflow
  unchanged (bots default to loopback). Released 0.16.0 via git-flow.

# 2026-07-25 — Multi-target scenarios: `scenario_run` (0.15.0)

## Done (0.15.0 — multi-target scenario orchestration)

- Built the third pillar of goal-level autonomy (`plans/goal-level-autonomy-2026-07.md` §3, owner
  Esc. 12: "server + client testing at the same time … MCP-side … no fragile glue"). `src/scenario.mjs`
  is a PURE orchestration engine: `runScenario(spec, {provisioners, actions})` provisions actors in
  declared order, runs coordinated steps, and GUARANTEES teardown in reverse order — even when a
  provision or a step throws, and even when a teardown itself throws (errors collected, cleanup
  continues). `validateScenario` fails structural mistakes up front (empty/duplicate actors, unknown
  kind/action, a step naming a missing actor) — nothing to tear down.
- Provisioners (by actor kind) + actions (by step verb) are INJECTED — the engine never hard-codes a
  backend, same anti-hack capability contract as `goals.mjs`/`flows.mjs`, fully unit-testable with
  fakes. Real wiring in `src/index.mjs`: provisioners `server`/`bot`/`client`/`agent` (thin closures
  over the live managers; each returns `{info, teardown}`, `info.targetId` marks a controllable
  executor), actions `wait`/`invoke`/`navigate`/`server_exec`. `invoke` drives ANY advertised
  capability on a bot/agent target — the backend-agnostic cross-target verb.
- `scenario_run` tool runs the scenario as a JOB (heavy — boots servers/clients); the job result is
  the report `{ok, provisioned, steps, teardown}`, `waitMs` optionally blocks for it inline. A bad
  spec errors at the tool boundary, not as a job to poll. Naming catch: the `agent` actor's own
  `kind:"agent"` would collide with the agent LAYOUT (paper|fabric), so the layout is a separate
  `layout` field.
- **Real proof** `scripts/scenario-smoke.mjs` + CI `scenario-smoke`: drives the ACTUAL MCP tool
  (`createServer()` all-real) — one `scenario_run` booted a REAL Paper 1.21.11 server + a REAL
  Mineflayer bot together, coordinated them (server console + bot chat/messages/status), and the
  engine tore both down. Ran it locally end-to-end: `ok:true`, bot spawned at `{x:9.5,y:-60,z:-2.5}`,
  teardown `[bot, srv]` both green, port released. No mocks.
  - Smoke lesson: the SDK client's per-request timeout (~60s) is shorter than a server boot, so the
    smoke uses the JOB pattern (start `scenario_run` with no `waitMs`, poll `job_status`) rather than
    one long blocking call — mirrors how a real caller drives a long scenario.
- **Tests:** 174 driver tests. `test/scenario.test.mjs` unit-proves the engine (declared-order
  provisioning, short-circuit on provision/step failure, LIFO teardown, collected teardown errors,
  validation, connect:false). Protocol tests over the in-memory client: server+bot together (with a
  plugin deploy), spawned-client + attached-agent as executors, step-argument guards, and boundary
  validation. c8 99.09% lines / 91.80% branches — gate (≥90 on all four) held. `check-links` 29 OK,
  `npm audit` 0 vulns, `build-docs` green.
